# Участие в разработке

Спасибо за интерес к проекту «СТАНКИН Расписание». Ниже описано, как сообщить
о проблеме, предложить улучшение и внести изменения в код.

## Как помочь

- Сообщить об ошибке — создайте issue по шаблону
  [Bug report](.github/ISSUE_TEMPLATE/bug_report.md).
- Предложить функцию — создайте issue по шаблону
  [Feature request](.github/ISSUE_TEMPLATE/feature_request.md).
- Внести изменения в код — отправьте pull request (см. ниже).

Перед началом большой задачи обсудите её в issue — это согласует подход
заранее и сэкономит время.

## Окружение и сборка

Требования:

- Android Studio Otter или новее
- JDK 25
- Android SDK: platform `android-37`, build-tools `36.0.0`
- minSdk приложения — 26

Сборка:

```bash
git clone https://github.com/overklassniy/STANKIN_Schedule_app.git
cd STANKIN_Schedule_app
./gradlew assembleDebug
```

### Конфигурационные файлы

Часть конфигурации не хранится в репозитории (см. `.gitignore`):

- `local.properties` — путь к SDK и опционально `sentry.dsn` для
  краш-репортинга. Без ключа Sentry собирается отключённым.
- `stankin.secret` — URL RSS-лент новостей и DSN Sentry. Создайте из примера:
  `cp stankin.secret.example stankin.secret`. Без файла раздел новостей
  будет пустым.
- `app/google-services.json` — конфигурация Firebase, обязателен для сборки
  модуля `:app` (плагин `com.google.gms.google-services`). Используйте файл
  из собственного проекта Firebase; для работы над отдельными модулями их
  можно собирать и тестировать без `:app`.

Никогда не коммитьте эти файлы и не включайте в них реальные ключи, токены
и пароли.

## Структура проекта

Проект многомодульный, слои выделены каталогами верхнего уровня:

- `app/` — точка входа, DI, навигация.
- `ui/<фича>` — экраны Compose, ViewModel, виджеты Glance.
- `domain/<фича>` — модели, use cases, интерфейсы репозиториев.
- `data/<фича>` — реализации репозиториев, Room, Retrofit, мапперы.
- `*/core` — общие компоненты и утилиты.

Новый код размещайте в модуле соответствующего слоя и фичи. Общую логику,
нужную нескольким фичам, выносите в `core`-модули, а не копируйте. Перед
добавлением нового компонента проверьте, нет ли в проекте готовой
реализации — существующий код следует использовать повторно или расширять.

## Правила кода и документации

- Комментарии и KDoc — только на русском языке, без эмодзи и декоративных
  символов.
- Публичные классы и методы документируйте русифицированным KDoc со
  стандартными тегами (`@param`, `@property`, `@return`, `@throws`, `@see`).
- Каждый Gradle-модуль содержит пару файлов `README.md` (русский) и
  `README_en.md` (английский перевод). При изменении модуля обновляйте оба
  файла в том же изменении.
- Заметные пользователю изменения отражайте в `CHANGELOG.md`.

## Проверки перед отправкой

Перед pull request убедитесь, что выполняется:

```bash
./gradlew :<module>:assembleDebug       # сборка затронутых модулей
./gradlew :<module>:testDebugUnitTest   # unit-тесты
./gradlew :<module>:detekt              # статический анализ Kotlin (конфиг detekt.yml)
./gradlew :<module>:lint                # Android Lint
```

- Для новой чистой логики (парсеры, мапперы, use cases, расчёты в `domain/`)
  добавляйте unit-тесты в `src/test/` модуля.
- Код с Android-зависимостями и UI проверяйте instrumented-тестами в
  `src/androidTest/` либо вручную на устройстве или эмуляторе.
- Новых предупреждений detekt и lint в затронутых модулях быть не должно.
- CI (`.github/workflows/unit-tests.yml`) прогоняет unit-тесты на каждый
  pull request — проверки должны быть зелёными.

## Коммиты и pull request

- Сообщения коммитов — на русском языке: короткий заголовок с сутью
  изменения, при необходимости — маркированный список деталей после пустой
  строки.
- Если изменение относится к issue, добавьте в конец сообщения `Refs #N`
  (часть работы) либо `Fixes #N` / `Closes #N` (задача решена).
- В описании pull request кратко укажите, что и зачем изменено, и ссылку
  на связанный issue.
- Один pull request — одно логическое изменение.
